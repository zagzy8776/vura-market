# Marketplace: buyer request → seller acceptance → payment & shipping (staged)

## Safety / deployment contract
- Migration `034_marketplace_sellers.sql` **and** `035_marketplace_order_requests.sql` must run **in order**, after a database backup and staging smoke test. Never assume the database is migrated from a Git commit.
- `VITE_COMMUNITY_ORDER_REQUESTS_ENABLED=true` gates buyer-facing links. Keep **unset/false** until the migrations and authentication tests succeed; default is disabled.
- This stage does **not accept payments, create a courier label, issue carrier tracking numbers or release seller payouts**. It must never advertise payment protection until a real payment provider/payout contract is in place.
- Existing Vura-managed product checkout and order ledger remain unchanged. Community orders are in their **own** tables.

## Reference identifiers
- Human order number: `YYYYMMDD + sequence (6-digit minimum)`, e.g. `20261028000421`. The server generates it from a database sequence, unique within Vura.
- Payment provider reference: generated by the payment integration after checkout initialization, independent from the order number.
- Courier tracking number: only from authenticated carrier APIs or verified partner events; never an arbitrary seller-entered value.
- Payout reference: separate, tied to a verified seller beneficiary and payout ledger.

## Stage 1 (implemented in this commit)
1. Buyer signs in, taps `Request to buy`, selects quantity and delivery area. A UUID request token makes submissions idempotent.
2. Server validates listing approval, stock, seller ownership, destination, and authenticated buyer, then creates an immutable price snapshot and order number.
3. Seller is alerted through a durable in-app notification plus best-effort OneSignal/email; a request has a six-hour confirmation deadline.
4. Seller sees requests at `/sell/orders` and may accept, decline, or mark item sold out. Marking sold out also pauses that listing.
5. Buyer sees responses at `/market-orders`; responses are recorded in `marketplace_order_events`.
6. Seller confirmation **does not** indicate payment was collected or inventory was reserved. Buyer sees a clear no-payment notice.
7. Buyer may cancel a pending/accepted request. All state mutations are server-authorized by buyer/seller ID, not client-supplied roles.
8. `marketplace_seller_dispatch_profiles` stores **private** pickup addresses, hidden from public API. `marketplace_shipments` is a future provider-owned shipment store; there is no public write endpoint.

## Stage 2: secure checkout & funds (not live)
- Introduce user phone collection/verification with SMS OTP, saved delivery addresses, private seller pickup address validation and beneficiary verification. Migration 035 introduces nullable phone fields without breaking older users.
- At seller confirmation, quote delivery through Shipbubble's rates API; freeze total and shipping quote before payment. An inventory reservation must be atomic with a strict expiry and release mechanism before enabling pay.
- Initialize payment at Paystack with an idempotent provider reference. **Never** mark paid from a browser callback; use authenticated provider verification/webhook.
- If merchant settlement and delayed payouts are contractually supported, hold an obligation in Vura's ledger, net platform fees, shipping costs and refunds, then send a transfer through provider beneficiary code when delivery/dispute conditions permit. **Ordinary Paystack subaccount splits settle immediately and are not escrow.**
- Payout attempts need immutable ledger entries, retries, idempotency, verified account details, transfer receipt/status webhooks, reconciliation, and admin review for anomalies.
- Shipping: validate sender and recipient address, request rates, book with carrier on API, save provider shipment ID/tracking URL, and map provider status to Vura timeline. Courier webhook signature must be verified; otherwise read authoritative carrier endpoint. Never fabricate movement.
- Buyer and seller updates: persistent in-app events first, then push/email. Seller nudges for pending acceptance and shipment handoff should use the scheduled queue/worker with delivery attempt auditing.

## Example state machine to implement with the payment integration
`awaiting_seller -> seller_accepted -> awaiting_payment -> payment_processing -> paid -> shipment_booked -> picked_up -> in_transit -> delivered -> payout_eligible -> payout_paid`
With independent exception states: `declined`, `expired`, `cancelled`, `payment_failed`, `shipment_exception`, `disputed`, `refunding`, `refunded`.
The first-stage order-request table intentionally has only the initial five statuses. Do **not** fake later states before implementation.

## Scaling recommendation
Avoid six or seven uncoordinated writable databases. Start with PostgreSQL as the order, inventory and finance source of truth, backups and read replicas; object storage for images, a queue for alerts/webhooks, Redis for ephemeral caching/idempotency, and search indexing when needed. Scale based on measured bottlenecks. Payment/stock/order writes must remain transactional.

## Verification checklist
- Apply migrations 034 and 035 to a staging DB.
- Run `npm run db:validate-migrations`, `npm run typecheck`, `npm run typecheck:api`, `npm run lint`, `npm run test:run`, `npm run build` before enabling the new storefront links.
- Sign in buyer → request approved seller listing → seller receives notification and order → accept / decline / sold-out → buyer sees response; no money changes hands.
- Try anonymous requests, self-buy, invalid quantity, duplicate request UUID, different seller accessing request, expired seller response, no stock, and concurrent requests.
- Verify public listing API never exposes seller street address or payout data. 
- Confirm older user signup, Vura-managed checkout, Studio authorization and admin reviews still work.
